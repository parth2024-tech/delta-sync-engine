This plan covers everything that turns it into a real working product: persistent storage, the sync wire protocol, an authenticated dashboard with live metrics, and a downloadable reference CLI. ## Execution Order (top → bottom, do not reorder) ```text Step 1  Cloud + Auth  ─────►  Step 2  Schema + RLS │ ▼ Step 3  API key system │ ┌───────────────────────┼───────────────────────┐ ▼                       ▼                       ▼ Step 4 Sync routes      Step 5 Server fns         Step 6 Storage (/api/public/sync/*)   (dashboard data)          (block blobs) │                       │                       │ └───────────────────────┼───────────────────────┘ ▼ Step 7  Auth UI + guarded layout │ ▼ ┌───────────────────────┼───────────────────────┐ ▼                       ▼                       ▼ Step 8 Dashboard       Step 9 Files+Versions    Step 10 Jobs+Keys │ ▼ Step 11  Reference CLI │ ▼ Step 12  QA, security scan, polish ``` --- ## Step 1 — Enable Lovable Cloud & Auth - Call `supabase--enable` to provision Postgres + Storage + Auth. - Configure auth providers: email/password (default) + Google via Lovable broker. - Verify `auth-attacher` is registered in `src/start.ts` (required so authenticated server fns receive the bearer token). **Deliverable:** Cloud connected, signup/login flows callable from the browser client. --- ## Step 2 — Database Schema & RLS Create one migration with all tables. Every user-data table has RLS enabled with policies scoped to `auth.uid()`. | Table | Purpose | Key columns | |-------|---------|-------------| | `profiles` | display name, avatar | `id` (FK→auth.users), `display_name` | | `files` | one row per logical file path per user | `id`, `user_id`, `path`, `current_version_id`, `total_size`, `created_at` | | `file_versions` | immutable version history | `id`, `file_id`, `version_no`, `size`, `total_blocks`, `block_size`, `content_sha256`, `created_at` | | `blocks` | per-version block index pointing into Storage | `id`, `version_id`, `block_index`, `offset`, `length`, `weak_hash` (int8), `strong_hash` (text), `storage_key` (text) | | `sync_jobs` | one per push/pull | `id`, `user_id`, `file_id`, `direction` (push/pull), `bytes_transferred`, `bytes_saved`, `status`, `started_at`, `finished_at`, `error` | | `api_keys` | hashed bearer tokens | `id`, `user_id`, `key_hash` (sha256 hex), `prefix` (first 8 chars for display), `label`, `last_used_at`, `revoked_at`, `created_at` | **Indexes:** `blocks(version_id, block_index)`, `blocks(weak_hash)` (server-side delta), `files(user_id, path)` unique, `sync_jobs(user_id, started_at desc)`, `api_keys(key_hash)` unique. **Auto-create profile**: trigger `on_auth_user_created` inserts into `profiles` on signup. **Storage bucket**: `blocks` (private). Path convention: `{user_id}/{file_id}/{strong_hash[0:2]}/{strong_hash}`. Content-addressed → identical blocks across versions/files reuse the same object automatically. --- ## Step 3 — API Key System - `src/lib/api-keys.functions.ts` (auth-protected server fns): - `createApiKey(label)` → generates `dks_<random_32>`, stores SHA-256 hash, returns plaintext **once**. - `listApiKeys()` → returns prefix, label, last_used_at, revoked_at. - `revokeApiKey(id)` → sets `revoked_at = now()`. - `src/lib/api-key-auth.ts` (server-only helper): given `Authorization: Bearer <key>`, hash it, look up in `api_keys` (not revoked), update `last_used_at`, return `user_id` or null. Used by the sync routes. --- ## Step 4 — Sync Wire Protocol (Server Routes) All under `src/routes/api/public/sync/` so external CLI can call them. Every handler: 1. Reads bearer token from `Authorization` header. 2. Resolves to `user_id` via `api-key-auth`. 3. Uses `supabaseAdmin` scoped by `WHERE user_id = $resolved`. 4. Validates input with Zod (path lengths, sizes, hash formats). | Route | Method | Purpose | |-------|--------|---------| | `/api/public/sync/files` | GET | List user's files (path, current version, size). | | `/api/public/sync/signatures` | POST | Body `{path}`. Returns `{file_id, version_no, block_size, signatures[]}` for the latest version, or `null` if file is new. | | `/api/public/sync/upload` | POST | Body `{path, block_size, new_size, ops[]}` where each op is `{type:"copy", block_index}` or `{type:"literal", bytes_b64}`. Server: replays ops referencing existing `blocks` rows + writes new literal blocks to Storage, creates `file_versions` row, inserts `blocks` rows, updates `files.current_version_id`, records `sync_jobs` with `bytes_transferred` (delta size) and `bytes_saved` (new_size − delta size). Returns `{version_no, bytes_saved}`. | | `/api/public/sync/download` | POST | Body `{path, version?}`. Streams reconstructed file: server reads `blocks` ordered by `block_index`, fetches each from Storage, pipes into a `ReadableStream`. Sets `Content-Length` and `Content-Disposition`. | **Wire format**: JSON with base64-encoded literals. Future v2 can switch to multipart/binary, but JSON keeps the CLI simple and is fine up to ~50 MiB transfers. --- ## Step 5 — Authenticated Server Functions (Dashboard Data) `src/lib/sync.functions.ts` with `requireSupabaseAuth`: - `getDashboardStats()` → totals (files, versions, lifetime bytes saved, transfer ratio), 30-day series of `bytes_transferred` vs `bytes_saved` aggregated by day. - `listFiles({search?, page, pageSize})` → paginated files with latest version metadata. - `getFileDetail(fileId)` → file + versions array + per-version `bytes_saved` from `sync_jobs`. - `listSyncJobs({page, pageSize, status?})`. - All return plain DTOs (no Supabase model instances). --- ## Step 6 — Storage Wiring - Migration creates the `blocks` bucket (private). - RLS on `storage.objects` for bucket `blocks`: only owner of the path's `user_id` prefix can read/write — matches the route handlers' `WHERE user_id = $auth_user`. - Upload helper: `putBlockIfMissing(userId, fileId, strongHash, bytes)` — uses content-addressed path; skips upload if object already exists (cross-version dedup). --- ## Step 7 — Auth UI & Guarded Layout - `src/routes/login.tsx` (public): email/password form + "Continue with Google" button (Lovable broker). Redirect-back via `?redirect=` search param. - `src/routes/_authenticated.tsx`: pathless layout, `beforeLoad` checks `supabase.auth.getUser()`, redirects to `/login` if missing. Renders `<Outlet />`. - Replace stub `/dashboard` with `/_authenticated/dashboard` + similarly move file/job/key pages under the guarded layout. - Wire `onAuthStateChange` once in `__root.tsx` to invalidate router + react-query cache on login/logout. --- ## Step 8 — Dashboard Page `/_authenticated/dashboard`: - KPI grid: lifetime bytes saved, transfer ratio %, files synced, active in last 24h. - 30-day area chart (recharts): bytes_transferred (amber) overlaid on bytes_would_have_transferred (cyan) — visually shows the gap. - Recent jobs table (last 10) with per-row delta stats and link to file detail. - Empty state with "Create API key & install CLI" CTA. --- ## Step 9 — Files & Versions Pages - `/_authenticated/files` — searchable, sortable table (path, size, versions, last sync, savings). - `/_authenticated/files/$fileId` — header with file metadata, vertical version timeline (newest → oldest), and for each version a **block reuse heatmap** (same component family as the playground): green cells = blocks reused from the prior version, amber = newly stored. `/_authenticated/keys` page links to it. --- ## Step 12 — QA, Security & Polish - Run `security--run_security_scan`; fix any RLS gaps. - Update `sitemap.xml` (already exists) to include new public routes only. - Per-route `head()` metadata on every new page. - Loading skeletons on dashboard cards, error boundaries on every authed route. - Manual end-to-end test: signup → create key → install CLI locally → push a 1 MB file twice with a tiny edit → verify dashboard shows >95% savings → pull and diff against original. --- ## Technical Details (reference) **Wire-format size accounting**: `bytes_transferred = sum(literal payload bytes) + ops.length * ~12B overhead`. `bytes_saved = new_file_size − bytes_transferred`. Persist both per-job for honest dashboard math. **Content-addressed storage**: storage path uses `strong_hash`, so identical blocks across files and users would collide — scope by `user_id` prefix to keep RLS clean. Cross-user dedup is deliberately out of scope. **Why server-side delta is NOT the default**: the client computes the delta because it has the new bytes. Server only needs to validate that referenced `block_index`es exist for the current version of that file (prevents forged COPY ops from leaking other files' bytes). **Validation invariants in `/upload` handler**: 1. Sum of op lengths == declared `new_size`. 2. Every COPY's `block_index` exists in the latest version's blocks for that file. 3. Recomputed SHA-256 of reconstructed file matches a client-supplied `content_sha256` (defense in depth). **Out of scope (deferred to v3)**: real-time peer sync, end-to-end encryption, conflict resolution, multi-machine live mirroring, binary wire protocol, chunked resumable uploads >1 GiB. --- ## Estimated Surface - **Migrations**: 1 file, ~6 tables + RLS + storage bucket + trigger. - **Server fns**: ~8 functions across 3 files. - **Server routes**: 4 endpoints under `/api/public/sync/`. - **UI pages**: 6 new authenticated pages + login. - **Components**: `BlockHeatmap`, `JobsTable`, `KpiCard`, `BandwidthChart`, `ApiKeyDialog`. - **CLI**: ~400 LOC across 5 files + README. This slice is large but each step is independently shippable — the API works without the dashboard, the dashboard works without the CLI, and the CLI works once API + keys exist.
